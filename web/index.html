DSL Quick Guide & Syntax
  • Wrap each problem inside problem <Name> ... end_problem (# or // for comments).
  • Currently v1.0 supports 1 or 2 state variables and 1 control variable.
  • Supported operators: +, -, *, /, unary -, right-associative ^, parentheses, and numeric literals (no built-in math functions yet).
  • Key blocks:
    • state: and control: (comma-separated names)
    • parameter: (name = <expr> lines)
    • dynamics: ... end_dynamics (var' = <expr> per state)
    • initial: ... end_initial (var = <expr> per state; target: ... end_target is parsed in the AST)
    • horizon: <int> (>= 1)
    • bounds: ... end_bounds (var in [lo, hi] with lo < hi for all state/control variables)
    • cost: ... end_cost (optional running = <expr> and terminal = <expr>)
    • solve: ... end_solve (method = dynamic_programming, grid = [nx] or [nx, ny] with counts >= 2, and controls = <int> >= 2)
How Backward DP & Rollout Work
  • For a discrete-time optimal control problem over a finite horizon N, the solver works backward from k = N to k = 0.
  • It initializes the terminal cost on the discretized state grid.
  • At each step, it minimizes the sum of the running cost and the interpolated next-step value function across admissible control values.
  • Once the value table is computed, a forward rollout starts from x_0 and applies the optimal control at each step to recover the state and control trajectories.
DSL Syntax & Semantic Validation
  • Problems are specified declaratively inside a problem ... end_problem block.
  • Sections include: state, control, parameter, dynamics (x' = ...), initial, horizon, bounds, cost (running and terminal), and solve settings.
  • Before running the solver, the compiler checks state/control counts, interval validity (lo < hi), matching grid dimensions, and ensures all variables used in expressions are declared.
Grid Discretization & Curse of Dimensionality
  • Solution accuracy depends on state and control grid resolution, time step dt, and grid interpolation.
  • Because the number of grid points grows exponentially with state dimension—known as the curse of dimensionality—tabular backward dynamic programming is well suited for low-dimensional systems.
  • 1D and 2D benchmarks (such as the Double Integrator) perform well, but it becomes computationally expensive in higher dimensions.
